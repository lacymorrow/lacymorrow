## About

> A live storefront had to move platforms before its category got deplatformed, without losing a product, a URL, or a day of trading.

The owner didn't want new features. He wanted to stop being one policy update away from losing his business. His payment provider could drop his category at any time and take the storefront with it, so the job was to move a working store onto ground he controlled.

## The constraint nobody expects

Most of the advice he'd been given was about platforms: this one permits the category, that one doesn't. That advice is close to worthless, and working out why was the most valuable hour of the engagement.

A merchant account is not a gateway. A platform that permits your category is irrelevant if no processor will underwrite it, and a bank-issued merchant account is useless if it can't reach a gateway the platform actually supports. Sign the wrong account and you own a payment method that connects to nothing.

So the first thing written wasn't a migration plan. It was a one-page constraint brief: what to ask an acquirer before signing, which bridges connect a high-risk account to a supported platform, and what reserve and chargeback terms to pin down in writing. Everything else depended on getting that right.

## Moving a live store without breaking it

137 products, 358 variants, 20 collections, 23 pages, and real order history. The pipeline assumes it will be wrong at least once.

The module that talks to the live store throws on any mutation. Not "we're careful", the blast radius is zero because the code physically cannot write.

A diff tool compares intended catalog state against what actually landed, and exits non-zero while anything is unresolved, so an import can't run past an unanswered question. Every judgment call lives in a file with who approved it and when. Overrides can only resolve a flagged difference, never introduce a change of their own, so the audit trail can't be used to sneak something through.

The redirect builder checks that every target actually resolves and refuses to apply while any of them 404s. It found links that were already broken on the original store.

That last part keeps happening. A migration audit is the most thorough read anyone will ever do of a store, so it surfaces problems that predate the project: images dead at the source, a vendor typo splitting one brand into two, duplicate collections, a redirect pointing at an unpublished product. Those went back to the client as their own list.

**Tech stack:** Node &middot; Shopify Admin GraphQL API &middot; BigCommerce API &middot; parity-gated migration pipeline
